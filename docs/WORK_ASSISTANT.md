# 업무 비서 — 아이디어 메모북과 진행사항

원본 명세에 없던 축. "일을 시킬 수 있는 비서"가 되려면 대화 이전에
**기억과 상태**가 있어야 한다.

---

## 1. 메모북이 죽는 지점

아이디어 관리 도구는 대부분 **포착**을 개선하려 한다. 그런데 실제로 죽는 지점은
포착이 아니다.

```
떠오름 → 포착 → [ 여기서 죽는다 ] → 실행
                    ↑
              다시 안 본다
```

적어두기만 하고 다시 안 보는 메모는 없는 것과 같다. 그래서 이 설계는 두 축을
분리하고, **정리 쪽에 더 많은 장치를 둔다.**

| 축 | 요구 | 설계 |
|---|---|---|
| 포착 | 3초 안에 끝나야 한다 | 분류 요구 없음. 한 줄이면 됨 |
| 정리 | 강제되어야 한다 | 상태 기계 + 방치 감지 + 주간 리뷰 노트 |

---

## 2. 포착 — 분류를 요구하지 않는다

```python
vault.capture("쉴드캔 접지점 두 개로 늘려보기")
```

프로젝트도 태그도 상태도 안 받는다. **분류를 강제하면 포착이 느려지고, 느린
포착은 안 쓰인다.** 분류는 나중에, 리뷰 시점에 한다.

음성 경로에서는 라우터가 `IDEA_CAPTURE`로 분류하는 순간 자동으로 들어간다.

```
▸ "방금 아이디어 떠올랐는데 쉴드캔 접지점 두 개로 늘려보기"
  분류: IDEA_CAPTURE (점수 6.0, 격차 6.0)
  → 메모북 포착: idea-20260809-001 (state=inbox)
```

세션도 프로젝트도 없이 들어올 수 있어야 한다. 아이디어는 장비를 만지다가,
회의 중에, 퇴근길에 떠오른다.

---

## 3. 정리 — 상태 기계

```
inbox ──► triaged ──► active ──► done
   │          │          │
   │          ▼          ▼
   └───►   parked ◄──────┘
   │
   └───►  dropped
```

### `dropped`와 `parked`에는 이유가 필수다

```python
vault.transition(idea_id, "dropped")
# ValueError: dropped 상태에는 reason이 필요하다.
#             이유 없이 버린 아이디어는 6개월 뒤 같은 형태로 다시 떠오른다.
```

이것이 이 상태 기계에서 가장 실용적인 제약이다. "페라이트 코어 위치 변경"을
왜 버렸는지 안 적어두면, 반년 뒤 같은 생각이 떠오르고 같은 시간을 다시 쓴다.
이유가 적혀 있으면 그 자리에서 끝난다.

되살리기는 허용하되 흔적을 남긴다.

```markdown
> 2026-08-09: dropped 에서 active 로 되살림.
```

### 방치 감지

```python
vault.stale(days=14)   # 14일 이상 손대지 않은 inbox
```

> **이 목록이 길어지는 것이 메모북이 죽어가는 유일한 신호다.**
> 주간 리뷰에서 이것부터 본다.

`review_note()`가 이 목록을 맨 위에 올린다.

## 4. 진행사항 — 이벤트에서 생성되는 노트

노트를 손으로 쓰지 않는다. 원장에서 생성한다.

```bash
python3 -c "..."   # 또는 데모: python3 tools/demo.py
```

```markdown
# 2026-08-09 작업 노트 — EMC_Filter_Study

이벤트 13건. 이 파일은 이벤트 원장에서 생성된 뷰다 — 직접 고치지 말 것.

## 지시
- 현재 100메가 노이즈 마이너스 42dBm 기록해줘
- 터치스톤 파일 로드해서 s21 플롯하는 코드 짜줘

## 측정 기록
| 시각 | 항목 | 값 | 출처 | 확인 |
|---|---|---|---|---|
| 07:41 | 100MHz | -42dBm | ai | **미확인** |

> `origin: ai` 이고 미확인인 값은 보고서에 그대로 옮기지 않는다.

## 실행 검증
- 샌드박스 2회 중 2회 성공
```

### 출처 표시가 이 노트의 핵심이다

`origin` 필드가 여기서 눈에 보이는 값이 된다. 이 노트는 나중에 보고서 초안이
되고, 보고서는 설계 판단이 되고, 설계 판단은 제품이 된다. **어느 숫자를 사람이
확인했는지가 그 경로의 첫 지점에서 드러나야 한다.**

STT는 "마이너스 42"와 "마이너스 32"를 혼동한다. AI가 받아적은 값은 사람이
확인하기 전까지 미확인이다.

## 5. 개인 일정

### 권한 모델

| 기능 | enterprise | personal |
|---|---|---|
| 조회 | 허용 | 허용 |
| 생성 | 사용자 승인 | 사용자 승인 |
| 삭제 | **관리자 승인** | 사용자 승인 |

삭제에 높은 문턱을 두는 이유는 단순하다. **일정 삭제는 되돌릴 수 없고, 오분류
한 번이면 발생한다.** "내일 미팅 취소해줘"가 어느 미팅인지 애매할 때 AI가
추측하면 안 된다.

### 구현 순서

1. **로컬 `.ics` 읽기부터.** 캘린더 API 연동은 인증·권한·망분리가 모두 걸린다.
   Ainative가 `tools/make_calendar.py`로 `.ics`를 뽑는 것과 같은 접근이다.
2. 조회만 먼저. 쓰기는 승인 UI가 붙은 다음.
3. 알림은 하네스가 아니라 OS/캘린더에 맡긴다. 알림 시스템을 직접 만들면
   범위가 두 배가 된다.

### 사내판에서 개인 일정을 다룰 때

사내 프로파일의 볼트는 `vault/work`다. 개인 일정은 여기 들어가지 않는다.
사내판이 참조하는 일정은 **업무 일정만**이며, 그것도 조회 전용으로 시작한다.

## 6. "일을 시킨다"는 것의 실제 형태

비서처럼 쓰려면 다음 셋이 있어야 한다. 대화 품질은 그다음이다.

### 6.1 기억 — 어제 뭐 하다 말았는지 안다

```python
build_context(store, session_id, limit=20, total_budget=4000)
```

유형별 예산을 둔다. 샌드박스 stdout 하나가 컨텍스트를 다 먹는 것을 막는다.

| 이벤트 유형 | 예산(문자) |
|---|---|
| `ai.response` | 600 |
| `sandbox.result` | 400 |
| `cli.exec` / `screen.capture` | 200 |
| 그 외 | 300 |

### 6.2 상태 — 진행 중인 것과 끝난 것을 구분한다

아이디어 상태 기계가 그것이다. 여기에 Phase 1에서 `task` 이벤트가 붙는다
(`task.created` / `task.updated`는 스키마에 이미 있다).

### 6.3 판단 유보 — 확신 없으면 되묻는다

```
▸ "터치스톤 파일 로드해서 s21 플롯하는 코드 짜줘"
  분류: EMC_ANALYSIS (점수 2.0, 격차 0.0)  [되물음 필요]
```

1·2위 격차가 좁으면 조용히 틀린 에이전트로 넘기지 않고 되묻는다.
**틀린 자신감보다 되묻는 편이 낫다.** 이 임계값(`min_margin`)도 아티팩트에
있으므로 GEPA 최적화 대상이다.

## 7. 다중 AI 협업의 실제 배치

§8.2의 "GPT → Claude → Gemini CLI" 파이프라인은 고정 순서라 유연하지 않다.
작업 유형별 배치가 실제에 가깝다.

| 작업 | 배치 |
|---|---|
| 아키텍처 초안 | 한 모델이 초안 → 다른 모델이 반론 → 사람이 결정 |
| 코드 구현 | 로컬 모델 우선(빠르고 싸다), 막히면 상위 모델로 승급 |
| 리뷰 | **작성한 모델과 다른 모델**이 본다 |
| CLI 조작 | Gemini CLI 등 파일시스템 접근이 되는 것 |
| 하네스 개선 | 전부 GEPA 프로포저로 투입해 경쟁 |

마지막 줄이 이 설계의 특징이다. 상세는
[`GEPA_HARNESS.md`](GEPA_HARNESS.md) §5.

### PowerShell 환경

Windows 엔드포인트에서 도는 이상 `exec` 표면이 전부다.
[`AUDIT.md`](AUDIT.md) §E 참조. 요약하면:

- 읽기 전용 명령만 자동 실행
- 나머지는 **명령 전문을 보여주고 승인**
- 금지 패턴은 무조건 차단 + 원장 기록
