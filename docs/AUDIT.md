# PRD v2.0-harness 상세 점검

대상: 「Audio-Vision Work Harness Platform — System Specification v2.0-harness」
점검일: 2026-08-09

이 문서는 원본 명세를 **반려하지 않는다.** 방향은 맞다. 다만 지금 상태로 사내
기술검토에 올리면 깨질 지점들이 있고, 그 지점들이 대부분 **문서 안에서 서로
모순**되는 형태로 드러난다. 아래는 그 모순을 짚고 대안을 붙인 것이다.

심각도 표기: **차단** = 이대로 착수하면 반드시 막힌다 / **중대** = 재작업을
유발한다 / **보완** = 지금 고치면 싸게 끝난다.

## A. "Harness First"라 선언하고 모델부터 산다 — **차단**

§3.1은 이렇게 쓴다.

> 모델보다 하네스를 우선 설계한다.

그런데 §16.1의 첫 줄은 GPU이고, PRD v1 §5는 H100 80GB ×2 또는 A100 80GB ×4를
권장한다. 개략 1.5~2.5억 원 규모의 자본지출이며, 이를 정당화하는 **측정된
기준선이 문서 어디에도 없다.**

이것이 단순한 순서 문제가 아닌 이유는, 문서가 스스로 채택한 GEPA가 정확히 반대
방향을 가리키기 때문이다. GEPA의 핵심 보고는 **반사적 프롬프트 진화가 훨씬 적은
롤아웃으로 강화학습을 앞섰다**는 것이다. 하네스 우선이란 곧 "같은 모델로 더 나은
결과를 얻는 경로를 먼저 소진하라"는 뜻이다. 하드웨어는 그 경로가 고갈된 뒤의
선택지다.

**대안**

1. Phase 0을 신설한다. GPU 0장, 기존 PC, 클라우드/로컬 소형 모델.
   측정 대상: 분류 정확도, 샌드박스 1회 통과율, 재시도 횟수, 사람이 손댄 비율.
2. 이 수치가 하드웨어 요청서의 근거가 된다. "모델이 작아서 막혔다"를 **숫자로**
   보인 뒤에 GPU를 요청하면 통과하고, 못 보이면 그 요청은 통과하지 못한다.
3. PoC 단계 GPU는 RTX 6000 Ada ×2 또는 그 이하로 고정한다.

이 저장소의 Phase 0 코어는 GPU·도커·LLM·네트워크 없이 돈다. `python3 tools/demo.py`
가 그 증거다.

## B. 지연 목표가 산술적으로 성립하지 않는다 — **차단**

§2는 "인간-AI 간 대화 지연을 50ms~500ms"라 쓰고, §15는 아래를 목표로 든다.

| 항목 | 문서 목표 |
|---|---|
| 음성 응답 시작 | < 500ms |
| STT 완료 | < 1.5s |

**두 숫자는 같은 것을 재고 있지 않다.** 50ms는 WebRTC의 **전송** 지연이고,
사용자가 체감하는 것은 *말이 끝난 순간부터 첫 소리가 나기까지*다. 후자는 전송이
아니라 다음의 합이다.

| 구간 | 현실적 범위 | 비고 |
|---|---|---|
| 발화 종료 감지 (VAD hangover) | 200~500ms | **줄일 수 없는 하한.** 너무 짧으면 말 중간을 자른다 |
| 네트워크 왕복 (사내망 WebRTC) | 10~50ms | 문서의 50ms는 여기까지다 |
| STT (Faster-Whisper large-v3, 3~5초 발화) | 200~500ms | GPU·배치 상황에 좌우 |
| LLM 첫 토큰 (32B~70B, 로컬) | 150~600ms | 프롬프트 길이에 비례 |
| TTS 첫 오디오 (Piper) | 50~150ms | Piper는 이 구간이 빠른 편 |
| **합계** | **약 0.6 ~ 1.8초** | |

즉 **§15의 "<500ms"는 달성 불가능**하고, §2의 "50ms~500ms 티키타카"는 전송
지연을 응답 지연으로 오독한 결과다. 이 상태로 기술검토에 올라가면 이 한 줄 때문에
문서 전체의 신뢰가 깎인다.

> 위 표는 각 구성요소의 공개된 특성에 기반한 **추정**이다. 실측이 아니다.
> Phase 0에서 구간별로 실측해 이 표를 교체할 것.

**대안** — 목표를 구간별로 쪼개 다시 선언한다.

| 지표 | 정의 | 목표 |
|---|---|---|
| `t_ack` | 발화 종료 → 시각 피드백(오디오 펄스 점등) | < 150ms |
| `t_first_audio` | 발화 종료 → TTS 첫 소리 | < 1.2s (P50), < 2.0s (P95) |
| `t_transport` | WebRTC RTT | < 50ms |
| `t_barge_in` | 사용자 개입 → AI 발화 정지 | < 200ms |

`t_ack`을 따로 둔 것이 핵심이다. 사람은 **응답이 빠른 것**보다 **무시당하지 않는
것**에 훨씬 민감하다. 150ms 안에 UI가 반응하면 1.2초 응답도 느리게 느껴지지 않는다.
이 한 줄이 H100 한 장보다 체감 개선이 크다.

## C. Llama-3.1-70B와 Qwen2-VL-72B는 96GB에 함께 못 산다 — **중대**

§16.1은 PoC GPU를 RTX 6000 Ada ×2 (96GB)로 잡고, 추가 프롬프트 4는 그 위에
70B와 72B VLM을 **동시 서빙**하는 가이드를 요구한다. 개략 계산:

| 항목 | 4bit(AWQ) 기준 |
|---|---|
| Llama-3.1-70B 가중치 | 약 35~40GB |
| Qwen2-VL-72B 가중치 | 약 38~42GB |
| 소계 | **약 75~82GB** |
| 남는 공간 (96GB 중) | 약 14~21GB |
| vLLM 오버헤드·활성화·단편화 | 5~10GB |
| **실사용 KV 캐시** | **약 5~15GB** |

Llama-3.1-70B는 GQA(KV 헤드 8, head_dim 128, 80층)이므로 토큰당 KV가 fp16
기준 약 0.33MB다. 10GB면 약 3만 토큰. 단일 사용자·짧은 대화라면 돌기는 한다.
문제는 **VLM 쪽**이다. 1080p 화면 캡처 한 장이 수백~2천 visual token을 먹으므로,
화면 분석 두세 번이면 KV가 바닥난다. 동시 사용자가 둘만 돼도 붕괴한다.

또한 두 vLLM 프로세스가 같은 카드를 나눠 쓰려면 `gpu_memory_utilization`을
수동 분할해야 하고, 그 상태에서 텐서 병렬까지 걸면 운영 난이도가 급격히 오른다.

**대안** (우선순위 순)

1. **VLM을 7B로 내린다.** Qwen2-VL-7B는 스미스 차트·플롯 판독 수준에서 72B와
   실사용 차이가 크지 않다. 가중치 약 5GB. 이것만으로 문제가 사라진다.
2. 코더는 Qwen2.5-Coder-32B-AWQ(약 18GB)로 충분하다. §16.1이 이미 이 모델을
   1순위로 들고 있는데, 프롬프트 4만 70B를 가정하고 있다 — 문서 내 불일치다.
3. 그래도 70B가 필요하면 **동시 서빙을 포기**하고 요청 유형에 따라 스왑한다.
   모델 로딩에 수십 초가 들므로 라우터가 배치를 모아야 한다.

이 저장소의 `profiles/enterprise.json`은 1·2안을 채택했다.

## D. 망분리를 선언하고 클라우드 프로바이더를 병기한다 — **차단**

§14.1은 "인터넷 직접 연결 금지"라 쓴다. §8.1은 프로바이더 풀에 GPT·Claude·
Gemini CLI를 올린다. 둘은 양립하지 않는다.

이것은 문장을 고쳐서 해결할 문제가 아니다. **문서로 쓴 경계는 지켜지는지 확인할
방법이 없다.** 실제로 새는 경로는 "누가 개인 노트북에서 사내 s2p 파일을 열고
Claude에 붙여넣는 것"이지, 아키텍처 다이어그램이 아니다.

**대안** — 경계를 판정기로 옮긴다. `harness/policy/engine.py`가 그것이다.

- `egress` / `exec` / `capture` / `store` 네 표면을 모두 이 엔진이 통과시킨다.
- `enterprise` 프로파일은 `egress_default: deny`가 아니거나 클라우드 프로바이더가
  있으면 **로드 자체가 실패**한다 (`Profile.validate()`).
- 게이트 G-02가 매 CI에서 이 불변식을 확인한다. 느슨해지면 빌드가 깨진다.

에디션 분리 설계는 [`EDITIONS.md`](EDITIONS.md)에 있다.

## E. PowerShell이 유일하게 샌드박스 밖인데 정책이 없다 — **차단**

§5.1에 "PowerShell Hook — 명령 실행 추적", §9에 "PowerShell Guard"가 있다.
그런데 §9.1의 정책은 전부 **파이썬 도커 샌드박스**에 대한 것이다.

여기에 구조적 문제가 있다. **PowerShell은 정의상 호스트에서 돈다.** 그것이 존재
이유다(파일 정리, 장비 제어, 배포). 즉 샌드박스가 방어선이 될 수 없고, 이 시스템에서
유일하게 격리 없이 실행되는 컴포넌트다. AI가 생성한 문자열이 사내 Windows 엔드포인트에서
그대로 실행되는 경로이며, **위험도로는 이 시스템 전체에서 1위**다.

문서에는 "Guard"라는 단어만 있고 정책이 없다.

**대안** — `exec` 표면을 정책 엔진에 넣고 3단 판정으로 간다.

| 판정 | 대상 | 동작 |
|---|---|---|
| `allow` | 읽기 전용 명령 화이트리스트 | 즉시 실행 |
| `confirm` | 목록에 없는 것 **전부** | 명령 전문을 UI에 띄우고 사용자 승인 |
| `deny` | 금지 패턴 | 실행 불가, 원장에 기록 |

기본값을 `deny`가 아니라 `confirm`으로 둔 것이 중요하다. 전부 막으면 아무도 쓰지
않고, 안 쓰이는 통제는 우회된다. 금지 목록에는 최소한 다음이 들어가야 한다.

```
Invoke-Expression, iex, -EncodedCommand, Set-ExecutionPolicy,
New-Object Net.WebClient, Invoke-WebRequest, curl, wget,
Get-Credential, ConvertFrom-SecureString, Remove-Item -Recurse -Force,
reg add, schtasks, Start-Process
```

구현: `profiles/*.json`의 `exec_allow` / `exec_deny`, 시험:
`tests/test_harness.py::TestPolicy::test_powershell_dangerous_commands_blocked`.

## F. 화면 캡처의 유출 위험이 통째로 빠졌다 — **차단**

문서는 화면 캡처를 **기능**으로만 다룬다(§11). 그런데 화면 캡처는 이 시스템에서
가장 큰 데이터 유출 표면이다. 논리는 단순하다.

> 문서는 "EMC 설계 데이터 등 기업 핵심 기술 보호"를 핵심 제약으로 든다(PRD v1 §1).
> 그런데 EMC 설계 툴 화면 캡처는 **바로 그 핵심 기술 자체**다.
> 개인용 에디션에서 이 캡처는 클라우드 VLM으로 나간다.

게다가 캡처는 의도치 않은 것까지 담는다. 옆에 열려 있던 메신저, 메일 미리보기,
콘솔에 찍힌 토큰, 다른 프로젝트의 창.

**흥미로운 점**: Ainative가 이 문제를 이미 풀어놨다. `kb/schema.md`의 에셋 규칙이
`screened: true`가 아닌 이미지의 색인을 **빌드 단계에서 거부**한다. 사유도 같다 —
"사내 캡처에는 토큰·개인정보가 실제로 자주 들어 있다". 같은 규칙을 그대로 가져온다.

**대안**

1. 앱 단위 차단 목록을 강제한다 — 메신저, 메일, 비밀번호 관리자, 원격 데스크톱.
2. 캡처는 **전체 화면이 아니라 ROI(드래그 영역)만** 기본으로 한다. 전체 화면은
   명시적 선택으로만.
3. 캡처 → OCR → 비밀 스캔 → (탐지 시) 마스킹 후에만 모델에 전달.
4. `screened` 플래그 없는 캡처는 저장·전송 모두 불가.

구현: `PolicyEngine.check_capture()`, `profiles/*.json`의 `capture_deny_apps`.

## G. 이벤트 원장에 보존·개인정보 정책이 없다 — **중대**

§10.2의 스키마는 이렇다.

```sql
CREATE TABLE events (id, session_id, event_type, payload JSONB, created_at);
```

이 테이블에 들어가는 것: 음성 명령 원문, 화면 캡처, CLI 히스토리, AI 응답 전문.
즉 **영업비밀 + 개인정보의 혼합 저장소**다. 회의 중 음성이 잡히면 동료의 발화가
동의 없이 들어가며, 이 경우 개인정보보호법 적용 대상이 된다.

문서에는 보존기간·암호화·접근통제·마스킹 중 어느 것도 없다.

**대안**

| 항목 | 조치 |
|---|---|
| 마스킹 | 저장 **직전** 크리덴셜·주민번호 패턴 치환 (`prepare_for_store()`) |
| 보존 | 프로파일에 `store_retention_days`. 사내 180일, 개인 무기한 |
| 무결성 | 해시 체인. 원장이 사후 수정됐는지 확인 가능 |
| 추가 전용 | UPDATE/DELETE를 **DB 트리거로** 차단. 앱 버그로도 과거가 안 바뀐다 |
| 동의 | 다자 발화가 잡히는 환경에서는 녹음 고지가 선행돼야 한다 (법무 확인 필요) |

구현: `harness/memory/events.py`. 마지막 항목은 이 저장소가 판단할 수 없는
사안이며 **법무 검토가 필요하다**고 남긴다.

## H. 분류기가 최적화 불가능한 형태다 — **중대**

§7.2의 라우팅 규칙:

```python
if "s2p" in text or "smith" in text:
    return "EMC_ANALYSIS"
elif "python" in text or "스크립트" in text:
    return "PYTHON_TOOL"
```

**두 가지가 잘못됐다.**

첫째, 한국어 STT 출력에 대해 잘 동작하지 않는다. "S 파라미터"는 상황에 따라
"에스파라미터", "s파라미터", "에스 파라미터"로 나온다. 공백·표기 흔들림을
흡수하지 않으면 매번 빗나간다.

둘째 — 이쪽이 더 중요하다 — **최적화 대상이 파이썬 소스에 하드코딩돼 있다.**
§19가 GEPA로 "Tool Selection"과 "Prompt Template"을 개선하겠다고 선언하는데,
개선 루프가 손댈 수 있는 텍스트가 존재하지 않는다. §7.2가 §19를 무력화한다.

셋째, 의미론적으로도 틀렸다. **이 도메인에서 의도를 정하는 것은 도메인 명사가
아니라 동사다.**

> "10MHz 임피던스 매칭 **코드 짜줘**" → EMC 분석이 아니라 코드 생성이다.
> "터치스톤 파일 로드하는 **스크립트**" → s2p가 있어도 PYTHON_TOOL이다.
> "1기가 리턴로스 -12 **기록**" → EMC 용어가 있어도 MEASUREMENT_LOG다.

문서의 규칙은 명사를 먼저 보므로 이 셋을 전부 틀린다.

**대안** — 규칙을 `artifacts/router.rules.json`으로 뺐다. 엔진은 해석만 한다.

실측 (`taskbank/router.jsonl` 48건, `tools/gepa_run.py --eval`):

| | train (36) | holdout (12) |
|---|---|---|
| 문서 방식에 가까운 시드 규칙 | 0.778 | 0.667 |
| GEPA 40~60회 제안 후 | 0.972 | 0.750 ~ 0.833 |

시드가 틀린 항목이 위에 든 세 가지 함정과 정확히 일치한다(rt-001, rt-028,
rt-036). GEPA는 시드 규칙을 몰라도 실패 피드백만으로 이를 교정한다.

> holdout 개선폭(+0.08~0.17)이 train 개선폭(+0.19)보다 작다. 과적합이 일부
> 일어나고 있다는 뜻이며, 숨기지 않고 기록한다. 48건은 작은 태스크뱅크다.

## I. §19 GEPA는 명사 나열에 그친다 — **중대**

§19는 "수집 대상"과 "최적화 대상"을 목록으로 든다. 그런데 GEPA가 성립하려면
목록이 아니라 다음 넷이 필요하다.

| 필요한 것 | 원본 문서 | 없으면 |
|---|---|---|
| 인스턴스별 채점 태스크뱅크 | **없음** | 파레토 프런티어를 만들 수 없다 |
| 텍스트 피드백을 내는 채점기 | 없음 (스칼라만 암시) | 반사할 재료가 없다 |
| 텍스트로 선언된 최적화 표면 | 없음 (§7.2가 하드코딩) | 고칠 대상이 없다 |
| 승격 게이트 | 없음 | 개선인지 퇴행인지 모른다 |

넷이 없으면 GEPA는 "LLM한테 프롬프트 다시 써달라고 하기"로 전락한다. 그것은
GEPA가 아니다.

특히 **파레토**를 빠뜨리면 안 된다. 가장 흔한 오구현은 최고점 후보만 계속
변이시키는 것인데, 그러면 지역 최적점에 갇힌다. GEPA의 핵심은 인스턴스 단위로
승자를 보아, **평균은 낮아도 어떤 항목을 유일하게 맞히는 후보를 살려두는** 것이다.

상세 설계와 구현은 [`GEPA_HARNESS.md`](GEPA_HARNESS.md)에 있다.

## K. AI가 쓴 측정값과 사람이 읽은 값이 구분되지 않는다 — **중대**

§18.1 시나리오:

> "현재 100MHz 노이즈 -42dBm 기록하고 이전 측정과 비교해 줘."
> → CSV 업데이트

이 CSV는 나중에 보고서가 되고, 보고서는 설계 판단이 되고, 설계 판단은 제품이
된다. 그런데 그 -42dBm은 **STT가 잘못 들었을 수 있다.** "마이너스 42"와
"마이너스 32"는 한국어 음성에서 충분히 혼동된다.

문서에는 이 값의 출처를 표시하는 필드가 없다.

**대안** — 모든 이벤트에 `origin`을 필수로 둔다: `human` / `ai` / `instrument` /
`system`. 그리고 측정 이벤트에는 `confirmed_by`를 둔다. 일일 노트는 미확인 AI
기록을 **굵게 표시**한다.

```
| 시각 | 항목 | 값 | 출처 | 확인 |
| 07:41 | 100MHz | -42dBm | ai | **미확인** |

> `origin: ai` 이고 미확인인 값은 보고서에 그대로 옮기지 않는다.
```

`python3 tools/demo.py` 출력에서 확인할 수 있다.

## M. 아이디어를 붙잡을 경로가 없다 — **보완**

§10.3에 "노트 자동 생성"이 있으나, 이는 **세션이 끝난 뒤** 요약을 만드는 기능이다.
정작 필요한 것은 반대다. 아이디어는 세션 밖에서 떠오른다 — 장비를 만지다가,
회의 중에, 퇴근길에.

그리고 아이디어가 죽는 지점은 포착이 아니라 **정리**다. 적어두기만 하고 다시 안
보는 메모는 없는 것과 같다.

**대안**: 포착과 정리를 분리하고, 정리에 상태 기계를 둔다. 특히 `dropped`와
`parked`에는 **이유를 필수**로 한다 — 이유 없이 버린 아이디어는 6개월 뒤 같은
형태로 다시 떠오른다. 상세는 [`WORK_ASSISTANT.md`](WORK_ASSISTANT.md).

## N. Barge-in이 상태 머신에 반영되지 않았다 — **보완**

§8 이슈3이 barge-in 교착을 정확히 짚는다. 그런데 §7.1의 상태 머신에는
인터럽트 노드가 없다.

```
START → INTAKE → CLASSIFY → PLAN → EXECUTE → VERIFY → COMMIT
                                                  └ 실패 → REFLECT → RETRY
```

**대안**: 인터럽트를 상태 머신의 **일급 전이**로 넣는다. 어느 노드에서든
`INTERRUPT`로 갈 수 있고, 진행 중 작업은 취소가 아니라 **중단점 저장 후 보류**
(`parked`)로 간다. 취소하면 사용자가 "아까 하던 거"로 돌아올 수 없다.

또한 부작용이 있는 노드(파일 쓰기, 명령 실행, 일정 생성)는 인터럽트로 롤백되지
않는다. 그 노드들은 **중단 불가 구간**으로 표시하고, 인터럽트를 큐에 넣어 구간이
끝난 직후 처리한다.

## 원본 문서에서 그대로 유지할 것

점검이 지적 위주라 균형을 위해 명시한다. 아래는 잘 잡은 것들이며 손대지 않았다.

1. **음성-텍스트 분리 출력** (§2). 코드·수치·표를 읽어주지 않는다는 원칙은
   음성 인터페이스 설계에서 가장 자주 틀리는 지점이고, 문서가 이를 정확히 잡았다.
2. **이벤트 기반 비전 트리거** (§11.1). 30fps VLM 스트리밍이 비현실적이라는
   진단과 대안이 모두 옳다.
3. **Tool-calling 기반 RAG** (§12). 수치 배열을 임베딩하지 말고 샌드박스에서
   pandas/scikit-rf로 다루라는 판단은 정확하다. 이 문서에서 가장 좋은 통찰이다.
4. **`network: none` 샌드박스** (§9.1). 방향이 맞다. 다만 하드닝 플래그가
   더 필요하고, `network: none`이면 pip이 안 되므로 이미지를 미리 구워야 한다는
   점이 문서에 없다 — `harness/sandbox/policy.py`에 보완했다.
5. **Work / Personal 메모리 분리** (§3.3). 이 착상이 사내/사외 에디션 분리의
   출발점이 됐다.
