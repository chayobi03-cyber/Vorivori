# 로드맵

원본 명세의 4단계(5개월)를 조달 리드타임과 1인 개발 현실에 맞춰 다시 짠 것.

---

## 원본 대비 무엇이 바뀌었나

| | 원본 | 수정안 |
|---|---|---|
| Phase 1 | GPU 서버 + vLLM + LangGraph + 샌드박스 (1개월) | **Phase 0 신설.** GPU 없이 코어부터 |
| 전제 | 하드웨어 조달 완료 | 조달과 **병행**. 코어는 조달에 의존하지 않음 |
| 검증 | 단계 말 데모 | 각 단계에 **측정 가능한 완료 기준** |
| 총 기간 | 5개월 | 조달 제외 6~9개월 (1인 기준) |

핵심 변경 이유는 [`AUDIT.md`](AUDIT.md) §A와 §L이다. 요약하면:

- 문서가 "Harness First"라 선언하고 GPU부터 산다 — 순서가 뒤집혀 있다.
- GPU 조달만 2~4개월. 방화벽 UDP 개방 승인은 별도 수 주.
- 즉 **원본의 Phase 1은 조달만으로 소진된다.**

| 아티팩트 기반 라우터 | 완료 |
| GEPA 루프 (파레토 + 반사 변이) | 완료 |

| 품질 게이트 G-01~G-09 | 완료 |

**완료 기준 (달성)**

```bash
./ci/gate.sh          # 9/9 통과
python3 tools/demo.py # 지시 → 분류 → 정책 → 원장 → 노트 왕복
python3 tools/gepa_run.py --budget 60   # holdout 0.667 → 0.750~0.833
```

**측정된 것 / 안 된 것**

- 측정됨: 태스크뱅크 위 분류 정확도, GEPA 개선폭(5시드), 게이트 통과.
- 측정 안 됨: 실사용 정확도, 지연, LLM 프로포저 성능. **검증됐다고 쓰지 않는다.**

## Phase 1 — 실행 루프 (진행 중)

Phase 0의 "실행계획"을 실제 실행으로 바꾼다.
상세는 [`EXECUTION.md`](EXECUTION.md).

| 항목 | 상태 |
|---|---|
| 상태 머신 (INTAKE→…→COMMIT) | **완료** — LangGraph 대신 자체 구현 |
| **INTERRUPT 노드** | **완료** — 일급 전이, 중단 불가 구간, 체크포인트 |
| 자가 수정 루프 | **완료** — 승급·fatal 구분·동일안 감지 |
| `SubprocessBackend` | **완료** (격리 경계 아님. 개인판 전용) |
| 재시도 정책 아티팩트 | **완료** — GEPA 최적화 대상 |
| `DockerBackend` | 구현됨, **실행 미검증** (데몬 있는 환경에서 확인 필요) |
| `py-emc` 이미지 빌드 | Dockerfile 작성. **빌드 미검증** |
| 코드 **생성** (모델 연결) | 미착수 — Ollama 또는 소형 vLLM |
| 태스크 상태 관리 | 스키마·이벤트만. UI 미착수 |
| 일정 **생성**·삭제 | 미착수. 승인 UI 선행 |

**Phase 1 완료 기준 (측정)**

- 샌드박스 **1회** 통과율 (재시도 없이) — 이것이 이후 모든 개선의 기준선
- 성공까지 평균 시도 수
- 태스크뱅크 200건으로 확대 (실사용 발화 수집)

**이 단계의 산출물이 GPU 요청서의 근거다.** "모델이 작아서 막혔다"를 숫자로
보이면 요청이 통과하고, 못 보이면 통과하지 못한다.

| 지표 | 목표 |

| `t_first_audio` | < 1.2s (P50) / < 2.0s (P95) |

> 로컬 오디오 파이프라인이 더 빠르고 단순하며, 방화벽 UDP 50000~60000 개방
> 승인(수 주)을 선행시키지 않아도 된다.

## 병행 트랙 — 조달·승인

코어 개발과 **독립적으로** 진행한다. 막혀도 Phase 0~2는 계속된다.

| 항목 | 리드타임 | 선행 조건 |
|---|---|---|
| GPU 서버 품의·조달 | 2~4개월 | Phase 1 측정치 |
| 전산실 전원·냉각·랙 | 조달과 병행 | — |
| 방화벽 UDP 개방 (WebRTC용) | 수 주 | Phase 3 착수 전 |
| 모델 가중치 반입 | 수 주 | 매체 반입 절차 |
| 보안 검토 (샌드박스·PowerShell) | 수 주 | Phase 1 완료 |
| 녹음 고지 **법무 검토** | 미정 | Phase 3 착수 전 **필수** |

마지막 항목은 이 저장소가 판단할 수 없다. 다자 발화가 잡히는 환경에서
개인정보보호법 적용 여부는 법무 확인이 필요하며,
**Phase 3의 차단 조건**으로 둔다.

## 개인판 트랙

사내 조달과 무관하게 진행할 수 있다. 그리고 여기서 나온 실사용 데이터가
사내판 태스크뱅크를 먹인다([`EDITIONS.md`](EDITIONS.md) §4).

| 시점 | 항목 |
|---|---|
| 지금 | Phase 0 코어를 개인 PC에서 매일 사용 |
| Phase 1과 함께 | 클라우드 프로바이더 라우팅, 개인 일정 |
| Phase 2와 함께 | 크로스 디바이스 볼트 동기화 |

**개인판을 먼저 쓰는 것이 사내판 성공 확률을 올린다.** 매일 쓰이지 않는 하네스는
개선 신호가 없고, 개선 신호가 없으면 GEPA 루프가 굶는다.

## 명시적으로 안 하는 것

범위를 지키기 위해 적어 둔다.

| 원본 항목 | 판단 |
|---|---|
| 스마트홈 제어 (§6.2) | 하지 않는다. 하네스의 위험 표면만 늘린다 |
| Netlify 자동 배포 (§6.2) | Phase 2 이후. 망연계 프록시 승인 선행 |
| 30fps 실시간 비전 | 하지 않는다. 원본 §11.1이 스스로 기각했다 |
| PostgreSQL | 다중 사용자가 실제로 생기면 |
| 자체 알림 시스템 | OS/캘린더에 맡긴다 |
| 프로파일 전환 UI | 만들지 않는다. 전환이 쉬우면 실수로 전환된다 |
